# PROJECT: STRAIT OBSERVATORY
## 台海觀測所｜看見台海的每一天
### Taiwan Strait Military Activity Data Observatory

你是一位同時具備以下專長的資深創作者與工程師：

- Creative Front-end Developer
- Data Visualization Designer
- Information Designer
- Art Director
- Motion Designer
- Data Engineer
- Front-end Architect
- Accessibility Engineer

請為我開發一個完整、可公開使用的資料視覺化網站。

網站主題：

**中華民國國防部每日公布的中共解放軍臺海周邊海、空域活動統計。**

本網站不是即時軍事雷達，也不是軍事情報平台。

它是一個以公開歷史資料為基礎，協助一般人理解每日活動、長期趨勢及歷史變化的獨立資料視覺化作品。

---

# 00｜核心理念

網站的核心目標：

**讓一般人不只看到今天有幾架共機，而是能理解這個數字在歷史上代表什麼。**

例如：

今天公布 20 架次。

那麼：

- 最近七天平均是多少？
- 最近三十天平均是多少？
- 今天比最近一個月平均高多少？
- 今年活動最頻繁的月份是哪個？
- 今年與去年相比有什麼變化？
- 哪些日期活動明顯高於平常？
- 是否呈現持續增加、減少或波動？

希望使用者透過漂亮、直覺、可靠的資料視覺化，逐漸理解台海周邊軍事活動的變化。

## 重要定位

本作品必須兼具：

1. 資訊透明。
2. 歷史分析。
3. 美學設計。
4. 互動探索。
5. 資料可信度。
6. 易讀性。
7. 長時間觀賞價值。

不需要追求秒級或分鐘級的更新頻率。

**每日更新一次即可。**

只統計到昨天，或最近一筆已公布的完整資料，也完全可以接受。

但必須清楚揭露資料涵蓋日期。

# 02｜資料研究與技術驗證

這是正式開發之前必須完成的工作。

請先實際確認：

1. CSV 是否可下載。
2. CSV 是否允許程式讀取。
3. CSV 的欄位名稱。
4. 日期格式。
5. 各數值的單位。
6. 是否存在缺失值。
7. 是否存在歷史資料修正。
8. 是否提供國防部原始公告 URL。
9. 是否能辨識共機架次。
10. 是否能辨識逾越中線架次。
11. 是否能辨識共艦與公務船。
12. 是否有機型、活動空域等延伸欄位。

請建立明確的資料正規化流程。

不要將所有邏輯寫在 UI 元件內。

## 2.1 重要資料概念

### 公告日期

國防部每日資料通常統計：

**前一天上午 06:00 至公告當天上午 06:00。**

日期應使用公告日期。

不能直接當成一般 00:00 至 23:59 的日曆日。

### 架次

代表偵獲的航空器出動架次。

不一定等於不同飛機的實際數量。

### 逾越海峽中線

必須使用國防部公告所對應的統計定義。

不能與領空侵犯畫上等號。

### 防空識別區

ADIZ 不等於領空。

### 艦艇

請確認資料是否將共艦與公務船合併統計。

如果不同年份的統計口徑不同，必須清楚標示。

### 機型

如果某日只有機型名稱，沒有各機型架次，不得自行推算。

### 缺少公告

缺資料不代表零架次。

**Missing ≠ Zero。**

這是最高優先級的資料品質規則之一。

# 03｜資料更新策略

我不追求完全即時。

建議：

**每天台灣時間下午 14:00 更新一次。**

這是建議的排程時間，不代表國防部保證會在此前發布資料。

請使用 Asia/Taipei 時區。

## 3.1 更新流程

1. 下載最新公開 CSV。
2. 驗證 HTTP 狀態與資料格式。
3. 檢查資料日期。
4. 驗證必要欄位。
5. 與既有資料比較。
6. 更新新增紀錄。
7. 同步已修正的歷史紀錄。
8. 重新產生統計結果。
9. 更新資料版本資訊。

## 3.2 更新失敗

如果資料來源失敗：

- 保留最後一次成功取得的資料。
- 顯示最後成功更新時間。
- 顯示最新資料涵蓋日期。
- 不可假裝資料已更新。
- 不可自動補上零值。
- 不可使用臆測數字填補。

## 3.3 更新架構

優先採用簡單、可靠的方案。

例如：

- GitHub Actions 每日排程。
- Serverless Function。
- 靜態 JSON 快取。
- 必要時建立小型資料庫。

如果網站可以透過每日產生靜態 JSON 運作，就不必一開始導入大型資料庫。

請依現有專案環境選擇。

## 3.4 資料版本

保留：

- 來源 URL。
- 抓取時間。
- 最新公告日期。
- 成功更新時間。
- 資料筆數。
- 資料檢查結果。
- 必要的版本識別。

如果來源網站修正歷史資料，網站應重新計算歷史統計。

這個作品與我其他的生活觀測網站屬於同一個創作系列。

因此不應直接沿用可愛 NPC、活潑轉蛋或遊戲競賽的呈現方式。

我希望發展成：

**沉靜、理性、克制，但仍然具有設計感的資料藝術。**

- Swiss Graphic Design

可以保留：

## 4.2 避免

不要使用：

- 軍事雷達 UI

## 4.3 配色

請探索具有成熟設計感的配色。

例如：

克制、清楚、具有資訊設計感。

### Palette B：鼠尾草綠 × 深墨綠 × 陶土紅

成熟、安靜、帶有印刷質感。

較具實驗性與藝術感。

像一本精緻的年度統計出版品。

# 11｜重要數據與比較方法

我希望所有重要數字都有參考值。

例如：

「今日共機 20 架次」

單獨看這個數字，其實沒有太多意義。

應該搭配：

「最近 30 個有效觀測日平均：12 架次」

以及：

「高於近期平均約 67%」

以上只是示意。

實際數字必須從資料計算。

## 11.1 建議指標

### 共機架次

當日觀測值。

### 逾越中線架次

當日觀測值。

### 越線比例

逾越中線架次 ÷ 共機架次。

若共機架次為零，不應顯示不具意義的比例。

### 艦艇艘數

須確認統計是否包含公務船。

### 7 日平均

最近七個有效觀測日平均。

### 30 日平均

最近三十個有效觀測日平均。

### 歷史百分位

例如：

「高於過去一年 80% 的有效觀測日。」

這是百分位概念，不代表風險機率。

請在介面中清楚說明。

## 11.2 平均值與缺日

如果最近 30 個日曆日只有 28 天有資料：

不能直接把另外兩天當成零。

請選擇明確的統計方式：

A. 最近 30 個有效觀測日。

B. 最近 30 個日曆日中的有效觀測值。

但必須在 UI 中清楚標示。

## 11.3 避免誤導

不要直接把：

共機架次增加 50%

寫成：

「台海危機增加 50%。」

軍事活動量不等於戰爭風險機率。

這個網站只呈現可驗證的活動數據與歷史比較。

# 13｜每日摘要文字

我希望網站可以自動產生一句簡潔的資料摘要。

例如：

「最新公布的共機架次高於最近三十個有效觀測日平均。」

「最近七個有效觀測日的平均共機架次低於前三十日平均。」

這些敘述應由明確的統計規則產生。

尤其不要自動產生：

- 中國準備發動戰爭。
- 台灣即將遭到攻擊。
- 某次行動是為了某項政治事件。
- 今日危機等級大幅升高。

除非有可靠且明確標示的外部證據，否則不應加入這類解讀。

**本網站是資料觀測，不是軍事意圖推測平台。**
